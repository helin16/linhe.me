# Research: Online lobby for Turbo Tumble

## R1. Room list: HTTP polling, not a second WebSocket

- **Decision**: `GET /relay/<game>/rooms` returns JSON (open rooms with a free spot, newest first,
  `Cache-Control: no-store`). The game polls it every 1.5 s while the Online popup is open (`LIST_POLL_MS`), so a change shows within 2 s including the request.
- **Rationale**: meets SC-003 (≤2 s) with no subscription bookkeeping on the relay; one route on the
  existing `node:http` server; Caddy already proxies `/relay/*` for any method; same origin, so
  `connect-src 'self'` covers it.
- **Alternatives**: a watch WebSocket with pushed updates (faster, but subscriber sets, debouncing
  and per-address counting for read-only sockets — more code for no visible gain at 2 s).

## R2. Names generated by the relay

- **Decision**: the relay picks the name when the room is made: adjective + animal from two fixed
  word lists in `relay/names.ts` (~40 × 40 = 1,600 names), retrying until unique within the game,
  like room codes. Sent to clients in `hello`.
- **Rationale**: uniqueness has to be checked where all rooms are known (two hosts at once, FR-002);
  generic, so any game gets names; fixed lists need no filter (clarification Q1).
- **Alternatives**: name made in the browser and checked by the relay (two round trips, can collide).

## R3. Waiting / racing state and countdown live on the relay

- **Decision**: a room is `open` (waiting) or `locked` (racing). The relay records when it last
  opened and sends `openFor` (ms since then) in `hello` and in a `room` frame on every change.
  Each client's deadline is `now − openFor + COUNTDOWN_MS` (60 s, game constant). The host
  (lowest slot) sends control frames: `room-lock` (race starting), `room-open` (race over),
  `room-close` (Cancel). The relay ignores them from anyone else.
- **Rationale**: one clock (the relay's) keeps everyone within 1 s (SC-004) and survives host
  hand-over (Q2) because the new host reads the same deadline; joining a locked room is refused by
  the relay (FR-009); the list is just open rooms with free spots (FR-004).
- **Alternatives**: host-only timer sent to guests (lost on host drop); relay starts races itself
  (game logic in the relay, breaks FR-013).

## R4. Room size on create

- **Decision**: `wss://…/relay/<game>/new?size=N`; the relay accepts `MIN_ROOM_SIZE` (2) up to
  `RELAY_ROOM_SIZE` (now default 12) and refuses anything else with 4400. Turbo Tumble offers 4–12
  (`ROOM_SIZES` in the game). `hello` carries `size`.
- **Rationale**: the relay enforces the cap without knowing the game; the game owns its own range.

## R5. Twelve karts in the game

- **Decision**: build `MAX_SLOTS` (12) karts once; the race uses the first `fieldSize()` (4 offline,
  room size online); the rest are hidden and skipped by drive, collisions, ranking, HUD and network
  state. Twelve racer looks (names and colours) in `RACERS`. Grid: 2 per row, 6 track points per row
  (12 karts = 6 rows, 36 of 600 points). Slot ↔ kart mapping uses the room size instead of 4.
- **Rationale**: smallest change to the existing kart array; offline stays at 4 (Q4).
- **Load**: 66 collision pairs; state messages ≤ 12 × 11 numbers (~1.2 KB, under the 8 KB cap);
  each browser still sends ~20 updates/s, under the 40/s rate limit; ≥10 updates/s per kart (SC-008).

## R6. Testing the 60-second countdown

- **Decision**: Playwright's `page.clock` fast-forwards the browser clock; relay e2e checks
  `openFor` directly.
- **Rationale**: no test-only setting for the countdown; tests stay fast.

## R7. List rate limit

- **Decision**: a token bucket per address for the list route (`RELAY_LIST_RATE`, default 5/s,
  burst 5); over it → HTTP 429. Buckets are dropped on the existing log interval.
- **Rationale**: FR-014; polling every 1.5 s uses ~0.7/s, leaving room for several tabs or a few
  players behind one shared address.
