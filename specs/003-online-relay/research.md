# Research: Online multiplayer for Turbo Tumble

Versions checked 2026-10-28: `ws` 8.22.0, `@types/ws` 8.18.2; Ubuntu 26.10 offers `nodejs` 24.19.

## R1. WebSocket server

- **Decision**: the `ws` package (8.22.0) for the relay's WebSocket server; browsers and tests use
  the built-in `WebSocket` client (Node 22+ has it globally).
- **Rationale**: Node has a WebSocket client but no server API; `ws` is the standard, dependency-
  free server (constitution VI: one dependency, with a reason). It supports per-message size limits
  (`maxPayload`) and ping/pong natively.
- **Alternatives considered**: hand-rolled upgrade handling on `node:http` (frame parsing, masking,
  fragmentation: a security risk to write by hand); Socket.IO (protocol and client library the game
  doesn't need).

## R2. Running the relay on the server

- **Decision**: Node 24 from Ubuntu's repository on the VPS. The relay is bundled at deploy time
  into one ESM file (`dist-relay/relay.mjs`, build output like `dist/`) with `ws` inlined, run by a
  hardened `systemd` service (`ExecStart=node …`, found on systemd's own search path, so no binary path in the repo; `DynamicUser`, `NoNewPrivileges`, read-only system, memory cap,
  `Restart=always`, `RestartSec=2`). The service file is generated by `scripts/deploy.ts` from
  configuration, so no server paths sit in the repo (constitution VIII).
- **Rationale**: nothing to install on the server but Node; the exact `ws` version comes from
  `yarn.lock` (constitution I). Restart within 2 s meets SC-006 (10 s).
- **Alternatives considered**: copying `relay/` plus `node_modules` and installing on the server
  (Yarn and lockfile on the server, slower deploys); Docker (more moving parts for one process).

## R3. Addresses and Caddy

- **Decision**: clients connect to `wss://<site>/relay/<game>/new` to create a room, or
  `wss://<site>/relay/<game>/<CODE>` to join. Caddy reverse-proxies `/relay/*` to the relay on
  `127.0.0.1:<port>` (WebSockets pass through `reverse_proxy` as is). The relay listens on
  localhost only. The game's relay base comes from `VITE_RELAY_URL`, defaulting to same-site
  `/relay/` (constitution V).
- **Rationale**: matches constitution V's `/relay/<game>/<room>`; Cloudflare proxies WebSockets on
  the free plan; TLS ends at Cloudflare/Caddy, so the relay needs no certificates.

## R4. Keeping connections alive through Cloudflare

- **Decision**: the relay pings every client every 30 s and drops clients that miss two pongs.
- **Rationale**: Cloudflare closes WebSockets idle for 100 s; players sit in the menu between races.
  Missed pongs also clean up dead connections, so rooms empty promptly (US1 scenario 6: 5 s target
  is met by the browser's close event on tab close; pings catch silent drops).

## R5. Rooms, codes and limits

- **Decision**: rooms live in a `Map<game, Map<code, Room>>` in memory only. Codes are 4 characters
  from `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (no 0/O/1/I/L), drawn with `crypto.randomInt`, retried on
  collision; normalised to upper case with spaces removed. Game names must match
  `^[a-z0-9-]{1,32}$` (game-agnostic, FR-009). Limits come from environment variables with
  defaults in one config module: 4 players per room, 8 KB per message (`maxPayload`), 40 messages
  per second per client (token bucket), 8 connections per address, 500 rooms in total.
- **Rationale**: FR-002/FR-005/FR-006/FR-007; 31⁴ ≈ 923,000 codes; the total room cap bounds memory
  on the 1 GB VPS.
- **Client address**: the relay trusts `CF-Connecting-IP` (Caddy forwards it; ports 80/443 only
  accept Cloudflare, so it can't be forged from outside), falling back to the socket address in
  development.

## R6. Message protocol

- **Decision**: JSON text frames. The relay owns three messages it sends (`hello` with `slot`,
  `peers`, `code`; `join`; `leave`) and closes failed joins with application close codes
  (4404 no room, 4409 room full, 4400 bad request, 4413 message too big, 4429 too many messages,
  4503 relay full). Everything a client sends is a game payload: the relay parses it, sets
  `from` to the sender's slot (so slots can't be spoofed) and forwards it to the room's other
  players. Turbo Tumble keeps its message kinds (`me`, `start`, `s`, `goo`, `pop`, `zap`) and
  `MsgType` values; `hello`/`join`/`leave` keep their values and meaning. The shared types and
  close codes live in `relay/protocol.ts`, owned by the relay and imported by the game.
- **Rationale**: FR-003 (same behaviour), FR-004/FR-009 (relay knows rooms, not games); one source
  for both sides (constitution VIII).

## R7. Game client changes

- **Decision**: a small `src/games/turbo-tumble/net.ts` wraps the WebSocket (connect, send, close,
  map close codes to messages); `game.ts` swaps `EventSource`/`fetch('send')` for it. The garage
  gains an online panel: "Create room", a code box with "Join", and once in a room the code with
  "Copy link". The join link is `gameRoute(slug)` plus `?room=<CODE>`; opening it pre-fills the code
  and shows the Join button (one tap, spec Q1). The query key is a named constant.
- **Rationale**: FR-001, FR-008, FR-013; keeps the race logic untouched.

## R8. Tests (constitution VII and V)

- **Decision**:
  - Unit tests (`node --test`) for the pure relay modules: code generation/normalising, room
    join/leave/host order, limits (token bucket, per-address counter), config parsing, and the game
    client's close-code → message mapping.
  - Relay end-to-end tests (`node --test`): start the real relay on a random port and connect real
    WebSocket clients: create/join/full/no-room, message forwarding with `from` stamping, isolation
    between two rooms and between two games with the same code, size/rate/address limits,
    leave on close, room cleanup when empty.
  - `yarn test` runs both with Node's coverage report and a 100% function-coverage threshold for
    `relay/` and `src/games/turbo-tumble/net.ts`.
  - Browser e2e with Playwright 1.64.1 (`yarn e2e`) in Chromium, WebKit (iPad, touch) and Firefox:
    two browser contexts create/join (by link)/race/leave and host hand-off, plus relay-down and
    unknown-code cases. `yarn deploy` runs it before uploading.
  - Incoming game messages from peers are validated (`parseGameMessage`) before the game uses them.
- **Rationale**: V requires relay isolation tests; VII requires unit tests with 100% function
  coverage for exported functions; Node's built-in runner and coverage need no new dependency.

## R9. Logging and privacy

- **Decision**: the relay logs only start-up, errors without payloads, and once a minute the number
  of open connections and rooms. No codes, names, addresses or messages are logged (FR-007).

## R10. Deploy

- **Decision**: `yarn deploy` also builds the relay bundle, uploads it beside the site (path from
  `DEPLOY_RELAY_DIR`), writes the `systemd` unit from config, restarts the service, and checks that
  `wss://<site>/relay/<probe-game>/new` returns a `hello` with a code. One-time server setup (install
  Node 24, add the Caddy `/relay/*` route) is documented in the README by role.
